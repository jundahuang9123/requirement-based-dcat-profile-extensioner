# DCAT versions and the DCAT state of each DCAT-AP release

A DCAT-AP extension is an extension of a DCAT-AP release. Each release is in turn a profile of one
W3C DCAT version, in the state that DCAT had on the release date. The tool therefore keeps **every**
DCAT version and **every** DCAT-AP release that ships SHACL in the repository. It pins each release
to the DCAT state the release itself names. A project works inside that state:

- retrieval offers that version's terms;
- verification flags terms the version does not have;
- conformance reports the DCAT version next to the base.

A new extension uses the **newest** DCAT-AP release, which builds on the newest DCAT (see "Defaults").

Everything below comes from the vendored files, at the commits named in
`backend/profile_extensioner/data/dcat/versions.yaml` and in each base's `profile.yaml`. Unverified
statements are marked **verify**.

| `dcat-3` | Candidate Recommendation Snapshot 2024-01-18; Proposed Recommendation 2024-06-13; Recommendation 2024-08-22 | `w3c/dxwg` `dcat/rdf/dcat3.ttl` @ ce5176c | `w3c/dxwg` `dcat/publication-snapshots/REC/Overview.html` (and `PR/Overview.html` as `spec-pr.html`) @ 2bc58b9 | 14 / 88 | 9 classes, 43 properties (including the inverse properties declared only by `owl:inverseOf`) |

Notes on the sources:

- **DCAT 2014 RDF.** `dcat2014.ttl` is the 2014 namespace document as W3C publishes it at
  `https://www.w3.org/ns/dcat2014`. The dxwg commit ece469f is titled "align dcat2014.ttl with the
  version currently published".
- **DCAT 2 RDF.** The term set and every domain and range equal those of `dcat/rdf/dcat.ttl` at
  d45e1eb (2019-10-17). That commit is from the Candidate Recommendation period, so the file also
  stands for the CR state.
- **DCAT 3 RDF.** The content did not change from f03a6dc (2023-02-02) to ce5176c (2024-10-16), so
  the file is the RDF of the CR, PR and REC periods. Later edits (2026-06, dxwg issues 1626 and
  1627) fix labels only and are not used.
- **DCAT 3 PR and REC texts.** Both yield the same class-property model
  (`model_equals_main_spec: true`).

`model.json` is generated by `scripts/build_dcat_versions.py` from the specification text, in
document order:
- a table headed "RDF Class:" opens a class;
- each table headed "RDF Property:" adds a property to that class, with its definition, range,
  domain and usage note;
- the "Sub class of" rows give DCAT's own class hierarchy. In DCAT 2 and 3, `dcat:Dataset` is a
  `dcat:Resource` and `dcat:Catalog` is a `dcat:Dataset`, so a class inherits the properties listed
  for its superclasses.

The model therefore holds **everything DCAT says applies to a class**. That includes the DCTERMS,
PROV, ODRL, FOAF, ADMS and SPDX terms DCAT reuses, not only the `dcat:` terms. For DCAT 3 the build
also extracts the eleven pairs of the section "Use of inverse properties".

`history.json` records, for every `dcat:` term:
- the versions that define it (`defined_in`);
- the versions that deprecate it (`deprecated_in`);
- the version that introduced it (`introduced_in`).

Examples:

| Term | Introduced in |
|---|---|
| `dcat:DataService`, `dcat:accessService`, `dcat:hadRole`, `dcat:startDate` | `dcat-2` |
| `dcat:DatasetSeries`, `dcat:previousVersion`, `dcat:hasVersion`, `dcat:inSeries` | `dcat-3` |

`dcat:size` is defined only by `dcat-2014`, where it is already deprecated.

Notes:

- **Two DCAT versions cited.** The 2.x releases name both the 2014 DCAT and DCAT 2. DCAT 2 keeps the
  2014 terms in the same namespace, so DCAT 2 is pinned and the double citation is recorded in

- **The 3.x import files.** `html/shacl/imports.ttl` of both 3.x releases imports
  `https://www.w3.org/ns/dcat2.ttl`, the DCAT 2 RDF, although the texts build on DCAT 3. Recorded in
  `notes`.
- **The 1.1 class table** links the DCAT classes to the Working Draft of 12 March 2013.
- **The optional-field rule.** 2.1.0 onward say: "Any property that is mentioned in DCAT applicable
  to a class but not explicitly is listed DCAT-AP is considered an optional field for DCAT-AP for
  that class."

## What the tool does with the DCAT state

- **Knowledge base.** A project's vocabulary index holds the DCAT terms as the **pinned** version
  defines them, with that version's domains and ranges. For example, `dcat:keyword` has
  `rdfs:domain dcat:Dataset` in DCAT 2014 and no domain in DCAT 2 or 3. Terms that only a later
  version defines are also indexed, marked `later` and with the version that introduced them, so that
  they can be recognised. A later term that the base itself already uses counts as `adopted`; for
  example, the DCAT-AP 1.2.1 shapes use DCAT 2's `dcat:startDate`.
- **Retrieval.** The reuse ladder is:
  1. elements the base defines on the atom's class;
  2. **properties the pinned DCAT lists for the class that the base does not profile**, scored in the
     DCAT specification's wording. For 2.1.x and 3.x the reason given is that the base treats such a
     property as an optional field of the class;
  3. other vocabulary terms;
  4. minting.

  Later-DCAT terms are ranked down (×0.5) and their reason names the version that introduced them.
  Terms the base deprecates (2.x/3.x `deprecateduris.ttl`, for example "replace dct:hasVersion with
  dcat:hasVersion") are ranked down and the replacement is named.
- **Prompts** (`propose-v2`, `repair-v2`). The PROFILE section states the DCAT state and the
  optional-field rule. Each candidate line carries "DCAT 2014 lists it for this class",
  "LATER DCAT: introduced in DCAT 2 (W3C Recommendation 2020-02-04)" or "DEPRECATED".
- **Verification.**
  - **D1:**
    - A DCAT term that only a later DCAT version defines is a warning that sends the change to a
      human (`needs_review`, policy `PipelineConfig.later_dcat_terms`: `review`, the default; or
      `forbid`, an error; or `allow`, a note).
    - A DCAT term defined only by earlier versions is an error.
    - A DCAT property used on a class that the pinned DCAT does not list it for, when the term has no
      declared domain, is an error.
  - **D2:** a term deprecated by the pinned DCAT (for example `dcat:size`, with the replacement
    `dcat:byteSize`) or by the base is an error.
  - **D3:** an inverse property (DCAT 3, section 7) is a warning. DCAT 3 says such properties "MAY be
    used only in addition to" the property they invert and "MUST NOT be used to replace them".
  - **V2** now reads `owl:unionOf` domains. DCAT 3 declares `dcat:hadRole` for `prov:Attribution` or
    `dcat:Relationship`, so `dcat:hadRole` on `dcat:Dataset` is a domain error.
- **Conformance C8.** Every DCAT term the extension uses is a term of the DCAT the base builds on.
  - A deprecated or removed term fails the check.
  - A later term that a human accepted is a warning, and the report names its version.
  - The summary reads "Conforms to DCAT-AP 1.1 (on DCAT 2014)".
- **Compiled output.**
  - The SHACL delta carries `dcterms:conformsTo` the dated DCAT Recommendation and a comment naming
    the DCAT state.
  - The documentation has a "DCAT state" section with the release's own quote, and a "Base history"
    section after a rebase.

| Base | Shapes (official, unmodified) | Obligations from | Deprecated-URI shapes |
|---|---|---|---|
| 1.1, 1.2 | `dcat-ap.shapes.ttl` from the release zip (implicit class targets) | release RDF usage notes | none |
| 1.2.1, 2.0.0, 2.0.1 | `dcat-ap_<r>_shacl_shapes.ttl` | release RDF usage notes | 2.0.x: `..._deprecateduris.ttl` |
| 2.1.0, 2.1.1 | `..._shacl_shapes.ttl` (+ `..._shacl_range.ttl`) | release RDF usage notes | `..._deprecateduris.ttl` |
| 3.0.0, 3.0.1 | `shacl/dcat-ap-SHACL.ttl` (+ `ranges.ttl` for 3.0.1) | quick-reference table of `index.html` | `html/shacl/deprecateduris.ttl` |

**Properties a specification lists without an official shape.** 1.1 and 1.2 have 14 such pairs, for
example `dcat:keyword` on `dcat:Dataset` (recommended) and `foaf:name` on `foaf:Agent` (mandatory).
They are base elements with their obligation and no other constraint. The tool treats them as
follows:
- "covered by the base" and the reuse ladder see them;
- V3 compares their obligation;
- no shape is invented.

**Typos in the release RDF, corrected** (`scripts/build_base_profile.py` `NAMESPACE_ERRATA` and
`TERM_ERRATA`, recorded in each `obligations.yaml` header). Every correction is to the IRI that the
release's PDF writes and the shapes use:
- `https://www.w3.org/ns/{dcat,prov,locn}#` becomes `http://...`;
- `https://www.w3.org/TR/owl-time/#time:` and `http://www.w3.org/2006/time/` become
  `http://www.w3.org/2006/time#`;
- `dcterms:acrualPeriodicity` becomes `dcterms:accrualPeriodicity`;
- `dcterms:mediaType` becomes `dcat:mediaType`;
- `dcat:servesdataset` becomes `dcat:servesDataset`.

Effect on the pilots: without these corrections, DCAT-AP 1.1 lost the obligation of
`dcat:contactPoint`, `dcterms:accrualPeriodicity` and `dcat:mediaType`. For example, the StatDCAT-AP
pilot reported frequency as "obligation unknown → recommended", where the specification says optional.

**Typos inside the official shapes, left as published** (the shapes stay unmodified):
- 2.0.x and 2.1.0 `http://data.europa.eu/r5ravailability`;
- 2.0.x `dcterms:licence` on `dcat:DataService`;
- 2.x `http://purl.org/dc/elements/1.1/isReferencedBy`;
- 1.2.1 shapes use `dcat:startDate` and `dcat:endDate` where the RDF names `schema:startDate` and
  `schema:endDate`.

## Defaults

The newest release (by release date) is the default base of a new project, unless the atom set
declares a base (`base_profile_ids`). Today that is **DCAT-AP 3.0.1 on DCAT 3**. Adding a newer
release or DCAT version to `data/` (with `scripts/build_base_profile.py` and
`scripts/build_dcat_versions.py`) makes it the default without code changes.

## Rebase

`POST /api/projects/{id}/rebase` (workbench: "Model & pipeline" → "Base profile") moves an extension
onto another release, and so possibly onto another DCAT. `engine/rebase.py` compares every change
under the old and the new base and its DCAT:

| Finding | Meaning | Default suggestion |
|---|---|---|
| `now_in_base` | the new base defines the element itself | `withdraw` if the change adds nothing beyond it, else `keep` |
| `base_dropped` | the new base no longer defines the element | `keep` (the change becomes an addition) |
| `base_changed` | the base constraint changed | `review` |
| `dcat_now_current` | a later-DCAT term is part of the new base's DCAT | `keep` |
| `dcat_now_later` | the new base's (older) DCAT does not define the term | `review` |
| `dcat_outdated` | the term is deprecated or removed in the new DCAT | `replace` |
| `deprecated_by_base` | the new base deprecates the term | `replace`, with the replacement it names |
| `mint_now_reusable` | a minted term has a counterpart in the new base or its DCAT | `replace` |
| `class_not_in_base` | the target class is not a class of the new base | `review` |
| `covered_claim_lost` | an atom covered by the old base is not covered by the new one | `repropose` |

After the comparison:
- Human decisions stay; a human-decided change gets the finding as a note.
- A machine-decided change with a finding that needs a decision goes to `needs_review`.
- Every change is verified again.
- The profile is recompiled and checked for conformance to the new base.
- The sign-off is withdrawn.
- The report is kept on the project (`Project.rebases`) and in the blackboard log.
