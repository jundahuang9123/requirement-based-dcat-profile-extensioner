\begin{abstract}
Interoperable dataset catalogs rest on the \ac{DCAT} and the \ac{DCAT-AP}, and domain extensions build on one
\acs{DCAT-AP} release by reusing terms, tightening its constraints and minting new ones: the guidance
asks use cases to justify new elements and tightened constraints, but does not fix how an element records the
requirement it serves.
This paper presents a pipeline in which a \ac{LLM} decides, for each requirement atom, whether the base already
meets it and otherwise fills typed change records that reuse before they mint; program code mints new identifiers
and checks every change, from term existence, legal refinement and the DCAT version the base builds
on to a verbatim quote of the atom and an obligation its modality licenses, a model judge assesses whether the
atoms support the change, and the model repairs failing changes in at most three rounds. % src: @5ffd56e B/contracts.py:595 (repair_rounds = 3); B/engine/verify.py:482-483 (check order); B/engine/prompts.py:24-72
Changes the machine cannot settle go to a person, whose decisions are final; the included changes are compiled
into a \ac{SHACL} delta, \ac{LinkML}, a \ac{DSV} profile and a trace matrix, eight rules, one a witness % src: @5ffd56e docs/conformance.md:41-51 and B/conformance/check.py:5-20 (C1-C8; C7 the witness)
validated with the official shapes, check that the extension conforms to the base, and only a person's sign-off
releases it.
We define reference deltas, each published profile minus its base, for the five extensions of the companion % src: RQ1 L14 and L381-388 (the five published extensions of its benchmark)
benchmark~\cite{anon2027rq1}, and compare the full pipeline with a rules baseline, a closed-book model and
variants without retrieval, repair or the judge over repeated runs.
