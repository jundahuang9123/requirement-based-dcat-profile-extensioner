\begin{abstract}
Domain extensions of the \ac{DCAT-AP}, a profile of the \ac{DCAT}, reuse terms, tighten base constraints and mint
new ones; the guidance asks use cases to justify new elements and tightened constraints but leaves open how an
element records the requirement it serves.
In our pipeline, a \ac{LLM} decides for each requirement atom whether a pinned base release already meets it and
otherwise fills typed change records that reuse before they mint. % src: @5ffd56e B/engine/prompts.py:24-72
Program code mints identifiers and checks every change, from term existence, legal refinement and the base's
DCAT version to a verbatim quote of the atom and an obligation its modality licenses. % src: @5ffd56e B/engine/verify.py:482-483 (check order)
The model judges whether the atoms support each change and repairs failing changes in at most three rounds; % src: @5ffd56e B/contracts.py:595 (repair_rounds = 3)
changes the machine cannot settle go to a person, whose decisions are final.
The included changes compile to a \ac{SHACL} delta, \ac{LinkML}, a \ac{DSV} profile and a trace matrix; eight
rules, one a witness validated with the official shapes, check conformance to the base, and only a person's % src: @5ffd56e docs/conformance.md:41-51 and B/conformance/check.py:5-20 (C1-C8; C7 the witness)
sign-off releases the extension.
We define reference deltas, each published profile minus its base, for the companion benchmark's five % src: RQ1 L14 and L381-388 (the five published extensions of its benchmark)
extensions~\cite{anon2027rq1}, and compare, over repeated runs, the full pipeline with a rules baseline, a
closed-book model and variants without retrieval, repair or the judge.
