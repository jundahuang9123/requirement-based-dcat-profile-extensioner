\paragraph{Application profiles and \acs{DCAT-AP} extensions.}
Profile engineering fixes what a profile contains, functional requirements included
\cite{nilsson2008singapore,coyle2009dcap}, and how it may change its base, not how a requirement becomes an element.
\ac{SEMIC}'s guidance resolves a use case by reuse, by tightening a base constraint but never loosening one, or by
minting in the profile's own namespace, and asks for use cases that justify new elements and tightened constraints,
not every element \cite{semicreuse2026}.
Practice keeps decisions at best as issues, resolution logs and links from requirements to use cases
\cite{dragan2019maintenance,statdcatap,w3cdcatucr}.
Dataspecer authors profiles of profiles and publishes them in \ac{DSV} and \ac{SHACL}
\cite{stenchlak2022dataspecer,klimek2024dataspecer,klimek2026dsv}; by our reading of its code it neither derives
profiles from requirements nor checks that their cardinalities and ranges refine the base, but its review of what a
changed base means for a dependent profile is the closest pattern we found for a machine that proposes and a person
who decides \verify{Dataspecer: code reading at one commit, nothing run}.
A visual profile editor models \ac{DCAT-AP} extensions in \ac{LinkML} \cite{moxon2026linkml}
\todo{anonymized reference to the profile editor}.
Neither the guidance nor Dataspecer fixes how an element records the requirement it serves, the base value it
tightens or the candidates it passed over, and that derivation is what we formalize and automate.

\paragraph{Requirements and reuse in ontology engineering.}
Ontology engineering specifies requirements before it models and looks for existing resources before it builds:
NeOn has scenarios that reuse ontological and non-ontological resources \cite{suarez2012neon}, and LOT records
verified requirements in a specification document \cite{suarez2009orsd} before each sprint searches existing
ontologies with their terms \cite{poveda2022lot}.
Competency questions mainly fix scope and evaluate the result \cite{monfardini2023}, and different elicitation
methods draw different questions from one story \cite{alharbi2026cq}.
The companion study judges against the base whether a requirement adds anything \cite{anon2027rq1}; this paper asks
how it adds, by tightening, reusing or minting, which can be judged only against the same base and the vocabularies
within reach.

\paragraph{\acs{LLM}-assisted ontology and shape generation.}
\acp{LLM} generate whole ontologies, or shapes for terms they are given.
Models elicit and generate competency questions \cite{zhang2024ontochat,lippolis2025bench4ke}, turn them into \ac{OWL}
one question per call or along a nine-step procedure in the released prompts of Memoryless CQbyCQ and Ontogenia
\cite{lippolis2025ontology}, % src: docs/literature-steps.md:14-15 (G1-S03 one CQ per call; G1-S04 nine-step procedure)
mine schemas from papers with expert feedback \cite{sadruddin2025schema} and assist domain modelers
\cite{prokop2024assistant}; extracting \ac{DCAT} metadata fills catalog records, not profiles \cite{busch2025dcat}.
NL2SHACL-Bench supplies the relevant ontology terms with each constraint description \cite{zhou2026nl2shacl},
text2shacl writes shapes per property of a railway ontology from its guide \cite{martinez2026text2shacl}, and Zhang et
al.\ generate ShEx schemas for knowledge graphs \cite{zhang2025schema}.
Closest to our pipeline is RIGOR, whose released implementation enriches a deterministic mapping of a relational
database: the model writes only deltas from retrieved context, a model judge approves, corrects or rejects each, a
failed delta is regenerated at most twice with the issues fed back, % src: docs/literature-steps.md:24 (G1-S13: at most three attempts per table, MAX_JUDGE_RETRIES = 2)
and every generated class and property records its source table or column \cite{fathallah2026rigor}.
IDEA2, the companion study's closest work, keeps expert votes and a PROV-O history of drafted competency questions
\cite{alharbi2027idea2}.
Like RIGOR we let the model change a fixed backbone only through checked deltas; we add typed change records instead of
model-written syntax, term choice among retrieved candidates of a pinned release, reasons for every mint, obligations
that a requirement's wording licenses, conformance to the base and a person's sign-off.

\paragraph{Reliability and evaluation of model outputs.}
Majority voting explains most of the gains of multi-agent debate \cite{du2024debate,choi2025debate,smit2024mad}, and
\ac{LLM} judges track human ratings \cite{liu2023geval,zheng2023judge} but are swayed by the order of answers
\cite{zheng2023judge,wang2024fair}, may prefer model-written text, score inconsistently
\cite{liu2023geval,stureborg2024inconsistent} and depend on the prompt \cite{yuan2024batcheval}.
These findings motivate one vote by default, % src: @5ffd56e B/contracts.py:597 (votes: int = 1)
independent votes being optional, symbolic checks before the model judge and machine decisions that a person can
overrule.
A cited source need not support the claim \cite{rashkin2023ais,gao2023alce}, so program code checks the trace
(\term{T1}) and a model judges attribution (\term{T2}).
Hosted models vary between runs \cite{atil2025nondeterminism,ouyang2025nondeterminism}, benchmarks leak into training
data \cite{sainz2023contamination}, and models lean on familiar words \cite{mai2024adapt} and falter on counterfactual
variants of familiar tasks \cite{wu2024reciting}, hence repeated runs on fresh stores and leakage controls
(Sect.~\ref{sec:setup}).
Information retrieval ranks systems reliably with incomplete pools and varying assessors
\cite{zobel1998reliable,voorhees2000variations}, with measures that ignore unjudged items \cite{buckley2004incomplete};
we take from this only that a change matching no reference element is not necessarily wrong.
Unlike the companion study, we report the share of included changes that match a reference element, a precision
against one published modeling, and adjudicate the rest instead of counting it as errors (Sect.~\ref{sec:benchmark}).
