\section{Changes for a DCAT-AP Extension}\label{sec:problem}

We distinguish changes by what they do to the base. A change \emph{refines} a property when it tightens a
constraint that the base states on a class and property, \emph{reuses} an existing property that the base does not
state on the class, and \emph{mints} a property in the extension's own namespace; it reuses or mints a class to bring
a class into the profile, and a \emph{usage note} adds guidance without a constraint. % src: @5ffd56e B/contracts.py:37-46 (six ChangeKind values), :699-706 (usage notes not scored)
Each atom first receives a \emph{disposition}: covered by the base, needs a change, out of scope (not about what a % src: @5ffd56e B/contracts.py:65-70 (four AtomDisposition values)
catalog record contains, such as system performance or an organizational process) or unclear. % src: @5ffd56e B/engine/prompts.py:62-64
These six kinds and four dispositions are our operational classification, informed by the order in which % src: LIT G3-S01 (four-rung ladder, implemented, Ours); docs/literature-steps.md:74
\ac{SEMIC}'s guidance resolves a requirement~\cite{semicreuse2026}; they are not a general taxonomy of ontology
changes. The atoms are the companion study's content atoms for finding and access, so its scope carries
over~\cite{anon2027rq1}. % src: RQ1 L61-64 (finding and access), L174-182 (content requirements scored)

In one sentence, the task is this: given a set of requirement atoms and a pinned \acs{DCAT-AP} release as the base,
decide for every atom whether the base already meets it, and produce changes that reuse before they mint (E1), trace
to the atoms they cover with an obligation those atoms license (E2), carry decisions that a person can inspect and
overrule (E3), and keep the extension conformant to the base (E4). % src: @5ffd56e docs/design.md:5-10 (goals); outline Sect. 2 (E1-E4 = pillars 1-4)

An \emph{atom} is one requirement: an identifier, a statement in plain words, a subject such as \emph{dataset}, a % src: @5ffd56e B/contracts.py:133-151 (Atom)
modality (must, should, may or unspecified) and an optional source reference; an \ac{IRI} or a prefixed name in % src: @5ffd56e B/contracts.py:32 (Modality)
the statement is an intake error, so the answer stays out of the input. The \emph{base} is a pair: a % src: @5ffd56e B/engine/intake.py:39-51 (both errors); B/contracts.py:134-140
\acs{DCAT-AP} release and the \acs{DCAT} version the release states it builds on, DCAT~2014 for 1.1 and DCAT~3 for % src: @5ffd56e B/contracts.py:238-250 (DcatBasis); B/data/base-profiles/dcat-ap-1.1/profile.yaml:33; B/data/base-profiles/dcat-ap-3.0.1/profile.yaml:43
3.0.1~\cite{dcatap11,semicdcatap301}. \verify{release quotes} We represent the base by its \emph{base elements}, % src: DCS §1.2 (the quotes are recorded in profile.yaml, not re-checked against the releases)
one per class and property it states, each with \emph{facets}: obligation, minimum and maximum count, range class % src: @5ffd56e B/contracts.py:194-217 (Facets, BaseElement)
or datatype, node kind, value list and pattern. The facets merge the release's official \ac{SHACL} shapes per class
and property with the obligation levels of its specification, because the shapes state only the mandatory ones, as % src: @5ffd56e B/knowledge/shacl_reader.py:79-106; B/knowledge/base_profile.py:233-240; @5ffd56e docs/conformance.md:34-36; KCU §1.3-1.4
\term{sh:minCount}; a pair the specification lists without a shape is a base element with its obligation only. % src: @5ffd56e B/knowledge/base_profile.py:76-81, 245-266; DCS §3
The default base, \acs{DCAT-AP}~3.0.1, has 131 elements on 33 classes: 20 mandatory, 39 recommended and 72 % src: paper/inputs/tool-facts-main-5ffd56e.txt:23
optional. The terms within reach form a vocabulary index of 926 to 933 terms per base: 12 vendored vocabularies, % src: paper/inputs/tool-facts-main-5ffd56e.txt:2, 6-14
the base's own terms and all 60 \acs{DCAT} terms, each marked relative to the base's \acs{DCAT} as current, % src: DCS §1.1 (60 terms over DCAT 2014, 2 and 3), §2.3; @5ffd56e B/knowledge/__init__.py:80-129
deprecated, adopted (a later term the base itself uses), later or removed (defined only by earlier versions). % src: @5ffd56e B/knowledge/dcat_state.py:127-146; B/knowledge/__init__.py:63-69 (adopted); DCS §2.2
From 2.1.0 on, the releases state that a property \acs{DCAT} lists for a class but the release does not is an % src: DCS §1.2 (2.1.0, 2.1.1, 3.0.0, 3.0.1: unlisted_dcat_properties optional); @5ffd56e B/contracts.py:246-248
optional field of that class; such a property is a reuse candidate, not a base element, so constraining it is an
addition. \verify{release text} % src: DCS §7 item 15; @5ffd56e B/engine/retrieve.py:134-156; B/engine/verify.py:319-320

A \emph{change} states one decision on one element: a target class and, for a property change, a property with % src: @5ffd56e B/contracts.py:385-420 (ProfileChange)
the facets it sets. Its \emph{coverage links} name the atoms it covers, each with a reason, a quote from the atom's % src: @5ffd56e B/contracts.py:334-340 (CoverageLink)
statement and a claim of full or partial coverage. Its \emph{facet justifications}, one for each facet it sets or
changes, give the base value, the new value, the status against the base and a reason; a mint also states why no % src: @5ffd56e B/contracts.py:343-356 (FacetJustification; status filled by V3: B/engine/verify.py:310-317)
candidate fits, and lists the candidates the model rejected when the model names them. With a rationale, a % src: @5ffd56e B/contracts.py:363-367 (MintJustification); B/engine/verify.py:370-391; ADD §H
self-reported confidence, the change's provenance and its decision, these records form the change's % src: @5ffd56e B/contracts.py:410-420
\emph{justification contract}. Program code, not the model, sets the kind from the facts: a mint when the term
lies in the extension's namespace, a refinement when the base states the class and property, a reuse otherwise % src: @5ffd56e B/engine/propose.py:191-204 (unchanged since 2b92d77: ISS header)
(Table~\ref{tab:kinds}). It also mints every identifier and writes the facet justifications, with the base value % src: @5ffd56e B/knowledge/__init__.py:38-45 (NEW:localName); B/contracts.py:116-119; B/engine/propose.py:287
beside the new one and, where the model gave no reason for a facet, the change's rationale. The obligation an atom % src: @5ffd56e B/engine/propose.py:240-266
\emph{licenses} follows its modality: must licenses mandatory, should recommended, may optional and unspecified % src: @5ffd56e B/contracts.py:712-715 (MODALITY_OBLIGATION)
recommended, our choice, so that an atom without a modality never licenses a mandatory property; a change is
licensed by the strongest of its atoms. The included changes compile to the \emph{ProfileDelta}, elements keyed % src: @5ffd56e B/engine/verify.py:463-471 (maximum over the covered atoms)
by class and property with their kind, facets and status against the base (added, tightened or loosened), the % src: @5ffd56e B/contracts.py:457-483; B/compile/model.py:52-78 (no element is unchanged: ISS E7.13)
contract that generated and reference deltas share. The criteria restate the four pillars of % src: @5ffd56e B/contracts.py:9-13 (mirrors the RQ2 scoring contract PE:1-28)
Sect.~\ref{sec:intro}.

\begin{description}
\item[E1 Reuse first and minimal.] An atom the base already meets gets no change, and the claim names base elements % src: @5ffd56e B/engine/prompts.py:35-38; B/engine/propose.py:108-112
  at least as strong as the obligation the atom licenses (B1). Otherwise a change tightens what the base states % src: @5ffd56e B/engine/verify.py:513-533 (B1)
  before it turns to another term, prefers a property that the base's \acs{DCAT} lists for the class, and reuses % src: @5ffd56e B/engine/prompts.py:35-46 (procedure steps 4-6)
  before it mints; a mint states why no candidate fits. Minimality is local: every change covers an atom, a % src: @5ffd56e B/engine/verify.py:370-371 (V4), 445 (T1 no atom)
  refinement tightens at least one facet, no obligation exceeds what the atoms license, and there is one element % src: @5ffd56e B/engine/verify.py:351-356 (V3 no_effect), 463-471 (T1), 493-510 (V5 duplicate_element)
  per class and property; no global minimum is computed.
\item[E2 Traced and licensed.] Every change covers at least one existing atom, and each link has a reason and a % src: @5ffd56e B/engine/verify.py:442-454
  quote that, lowercased and with whitespace normalized, occurs in the atom's statement; every facet a change sets % src: @5ffd56e B/engine/verify.py:86-87, 455-462
  or changes has a justification with the base value beside the new one and a reason; and a property change sets no % src: @5ffd56e B/engine/propose.py:240-266; B/engine/verify.py:472-474
  obligation above the strongest one its atoms license. Quoting and licensing are mechanical checks (T1); whether % src: @5ffd56e B/engine/verify.py:463-471 (not checked for class changes and usage notes)
  the atoms support the change, its other facets included, is a separate, fallible judgment (T2). % src: @5ffd56e B/engine/pipeline.py:221-244
\item[E3 Decided, inspectable and overrulable.] Every change carries its decision, who made it (a rule, the model % src: @5ffd56e B/contracts.py:91, 298-307, 378-382 (AuthorType, Provenance, Decision)
  or a person) and the inputs behind it, every model call included. A person can overrule any decision, no machine % src: @5ffd56e B/contracts.py:549-571 (LLMCallRecord with full prompts); B/engine/pipeline.py:493-555
  stage overwrites a person's decision, and only a person's sign-off releases the extension. % src: @5ffd56e B/engine/pipeline.py:58-60, 246-248, 283-285, 618-640; ENG §4
\item[E4 Conformant to the base.] Every constraint is added or tightened, never loosened or in conflict with the % src: @5ffd56e B/conformance/refinement.py:83-230 (unchanged since 2b92d77: ISS header); B/engine/verify.py:291-357
  base, by a legal-refinement order: a minimum may rise and a maximum fall, a range class may narrow to a known
  subclass, a value list or the admitted node kinds may shrink and an obligation may rise, but a datatype may not
  change. Minted terms are new and lie in the extension's namespace, reused terms exist, every \acs{DCAT} term % src: @5ffd56e B/engine/verify.py:95-158 (V1); B/conformance/check.py:149-168 (C3, C4)
  belongs to the base's \acs{DCAT} (a later one only by a person's decision, under the default policy), and base % src: @5ffd56e B/engine/verify.py:219-283 (D1-D3); B/contracts.py:604-606; B/engine/pipeline.py:260-263; B/conformance/check.py:64-99 (C8)
  and extension can be satisfied together. Because the compiled extension holds only shapes in its own namespace % src: @5ffd56e B/compile/shacl.py:27-32 (validate together with the base shapes); B/compile/model.py:43-44 (shape IRIs in the extension's namespace)
  and is validated together with the official shapes, data valid under the profile is valid under the base by % src: KCU §4.4 (the merged shapes contain every base shape, so the base-only branch of C7 cannot fire)
  construction; the conformance rules therefore test what this does not give: the documented constraints, joint % src: @5ffd56e docs/conformance.md:41-65 (C1-C8)
  satisfiability, term hygiene, the trace, \acs{SHACL} validity and the \acs{DCAT} state (Sect.~\ref{sec:compile}).
\end{description}

A published profile can also rest on modeling choices that no requirement states, and several modelings can meet
one atom; tacit knowledge, a known obstacle in elicitation~\cite{gervasi2013tacit}, leaves such choices unwritten. % src: RQ1 L223-227 (pattern)
When no atom asks for a reference element, its origin cannot be traced, and the evaluation leaves it outside the
denominator, as beyond the atoms' reach, not as a miss (Sect.~\ref{sec:benchmark}).

Unlike the companion workflow, whose needs stay retained until a person accepts them~\cite{anon2027rq1}, the % src: RQ1 L228-232
pipeline decides. A change is \emph{proposed}, then \emph{auto-accepted} by the decision policy or left % src: @5ffd56e B/contracts.py:81-89 (DecisionStatus); B/engine/pipeline.py:246-267
\emph{waiting for review}; a person \emph{accepts} or \emph{rejects} it; the model can \emph{withdraw} it in repair,
which is stored as rejected with its reason; and a repair, an edit, a merge or a new proposal \emph{supersedes} it. % src: @5ffd56e B/engine/pipeline.py:175-178, 311-331, 512-531; B/engine/consolidate.py:25-95; NOTES 7
The \emph{included} changes, those auto-accepted or accepted, form the extension. These are workflow states, not % src: @5ffd56e B/contracts.py:89 (INCLUDED_STATUSES); B/compile/model.py:47-49
guarantees of correctness. Only a person's recorded decision accepts a change, and that decision belongs to the % src: @5ffd56e B/engine/pipeline.py:493-536 (decided_by human:<name>)
team that builds the profile (Sect.~\ref{sec:setup}); only a person's sign-off releases the extension. An atom's % src: @5ffd56e B/engine/pipeline.py:618-640
coverage, from addressed to unaddressed, is the tool's own count and a machine state too: \emph{addressed} rests on % src: @5ffd56e B/contracts.py:72-79; B/engine/pipeline.py:430-449
the model's claim that a change covers the atom in full. Table~\ref{tab:criteria} in the appendix illustrates the
criteria.
